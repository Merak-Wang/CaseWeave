# Agent 运行、领域专家与可恢复任务

DSH 负责模型运行和领域专家，持久 worker 负责调度、命令回执、执行租约与恢复。主 Agent 和专家共享受控证据，Wiki 输入按任务固定版本。职责总览见 [架构](../ARCHITECTURE.md)。

## 1. 主 Agent 与专家

正式 preset 的 persona 只提供角色身份，使用 `complete: false` 与插件注册的检索、证据判断和协作规则组合；运行规则由实际拥有该行为的插件维护，避免另写一份旧版流程。DSH 的完整 persona 会在组装后屏蔽所有其他系统 section，工具仍可能可见，因此只检查工具列表或源码注册不足以证明规则生效。验收同时核对正式 persona 的 DSH 组装和真实请求 Session header。

持久 worker 的取消会显式中止该主 Agent 的专家批次，即使主 loop 已在业务问题处空闲。停止旧 Host 时先通知子分支，再释放执行租约；被中止的分支保留当前已提交证据和未完成状态，由替换 Host 按原任务/输入代次重新创建子会话。仅调用空闲主 Agent 的 cancel 不足以关闭仍在取证的独立子任务。

主 Agent 在首轮候选形成后读取 QueryPlan、分支状态、候选概要和覆盖缺口，再从 Wiki 目录自动路由领域专家。目录为空时使用通用零样本策略；小问题允许不分派专家直接判断。专家是带特定知识包/skill 的 Agent，可共用基底模型，不以创建固定角色数量为目标。

独立子任务与有限上下文可以支持并行取证，但需要明确分工和返回产物，不能让多个角色重复同一问题。此组织方式参考 [Anthropic 多 Agent 研究系统](https://www.anthropic.com/engineering/multi-agent-research-system)，性能收益仍需本项目验证。

| 角色 | 接收 | 提交 |
| --- | --- | --- |
| 主 Agent | 原始要求、最新状态、专家目录和发现摘要 | 领域路由、覆盖任务、综合判断、下一动作、停止理由 |
| 专家 | 具体目标、领域知识版本、候选/证据视窗、允许工具 | 策略、改写 query、逐条依据、反例、覆盖缺口与分歧 |
| Controller | 带状态版本的结构化建议 | 接受/拒绝原因、持久状态、受控检索或读取作业 |
| 调度器 | 已准入作业和依赖关系 | 并发执行、背压、重试、取消、可恢复结果 |

ExpertTask 必须有 taskId/branchId、queryRevision、目标、scope、已分配候选、Wiki release、可用工具、资源额度和预期输出类型。不同专家可以针对同一工单的不同业务解释检查；系统按查询签名去重相同搜索，复用证据，不重复付出 embedding/读取成本。

Finding 包含：结论类型、工单/证据引用、适用要求、支持与反对证据、仍缺什么、建议动作。主 Agent 综合这些产物并对最终判断负责，必要时重新打开原片段。专家提交中间判断不会直接发布最终报告；主 Agent 可以采纳逐条证据支持的批量判断，无须把所有详情再读一遍。

当前 `ticket_decide.delegate` 每批分派 1–3 个专家；目标/scope、当前候选（至多 20 条）、inputGeneration 和 Wiki release 均入权威状态。知识条目必须属于所选目录领域，省略时自动取至多 3 条；空库/校验失败使用 general，目录只在快查产生候选页后加载。子 Agent 由公开 `subagents.start('spawn')` 创建，独立模型上下文、禁止再委派，只允许 `ticket_expert` 搜索/读取/report。可信取证 skill 与不可信 Wiki 数据分开；Wiki 不能授予工具权限。

委派立即返回；每任务最多 3 个专家运行、6 个运行/待运行分支，允许追加不同 scope，拒绝相同分工重复委派。主 Agent 可在专家执行时继续审阅未分配摘要、补检和综合已返回发现。确实依赖未完成分支时调用 `ticket_wait`，由事件唤醒于首个相关结果，不轮询模型、不等整批。专家寿命属于任务协调器，不绑定已返回的委派工具请求。实际空闲时显示等待，主 Agent 有独立工作时与专家同时显示运行。

主 Agent 和专家默认用当前 L1 标题/摘要作逐条判断，`cN` 即合法概览依据。大关键词集合在后台保存；模型按小窗推进，达到所需数量/范围即可停止。只有可描述的事实缺口、来源冲突或原文核实需求才读取最小字段，不预设每个摘要都需全文复验。详见 [上下文](CONTEXT.md)。

搜索签名包含任务、快照、输入代次、query spec 和游标；同一签名的并发请求 single-flight，并在任务状态保存检索页供后续复用。读取同样去重，复用前重新验证主任务授权与 Provider 状态。逐条产物只接受该角色实际请求 manifest 中的本工单证据；主 Agent 通过 adopted_finding_id 保存采纳关系。相反 verdict 或专家明确报告的证据冲突撤销受影响确认，主 Agent 重读源片段、分类并提交 conflict_resolution 后才能重新确认。

主/专家无固定动作、请求次数或时间完成截止；工具错误返回具体字段和可执行修正，只检测同参数、同错误且无有效进展的重复循环。用户补充递增 inputGeneration，旧分支转 superseded，迟到产物拒绝；旧范围判断失去当前资格，但来源、候选、轨迹与历史核查路径保留。进程内短状态操作按父任务顺序提交，独立模型请求并发；MySQL 短事务继续校验输入代次与 worker fence。后台专家新增证据/发现与主判断兼容时不制造无效版本冲突，真正条件改变仍拒绝旧提交。迟到分歧会重新打开受影响判断，不能由先提交者覆盖。

页面快照和 SSE 的来源重新授权独立于慢搜索写入队列，读取 SQL 当前状态并向 Provider 重新核验。状态或输入版本在核验期间变化则重试；授权失效等状态变化仍通过 SQL 乐观版本检查提交，不能覆盖新输入或较新的证据。

## 2. 分歧的处理

不以投票数或“专家置信度平均值”判定真伪。多 Agent 辩论研究提示共识压力可能使正确判断转向错误，但其基准不等于通信工单；这里借鉴的是检查分歧依据而非照搬论文算法。[Free-MAD](https://arxiv.org/abs/2509.11035)。

| 分歧 | 下一步 |
| --- | --- |
| 对工单事实读取不同 | 核对来源/字段/版本，读取有决定性的处理记录或原对话 |
| 对“相关”的业务范围理解不同 | 主 Agent 依据原句、Wiki、实例及已答复信息自决；仅缺少不可推知的用户独有信息才询问 |
| Wiki 与当前工单冲突 | 当前来源证据优先，保留反例并交给知识更新 |
| 搜索覆盖判断不同 | 列出未查的具体方向，选择预期有信息增益的搜索 |
| 源字段矛盾或数据无法判断 | 保留未判定，报告范围限制；不能靠再辩论生成事实 |

流程为独立提出看法 → 对齐分歧类型 → 定向补证 → 主 Agent 复核。每轮要说明获得了什么新证据；没有新增依据的重复争论不继续。并发数和补证轮次根据收益/成本实验调整，不写死一个普遍正确的值。未解决分歧的工单不会混入确认结果。

专家的公开进度来自权威 `ExpertTask`：执行开始、读原文、搜索和提交发现记录 `activity.kind/at`，由任务 SSE 通知后读取公开快照。领域目录和实际 DSH 请求的知识引用分别展示。子 Agent 的 Session 身份在第一次 `agent/pre-step` 中、模型执行前持久化，避免快速报告已经可见而恢复记录仍指向旧会话；工作台的具体投影与阅读交互见 [工作台设计](WORKBENCH.md)。

## 3. 知识状态与动作

主 Agent 与专家默认工作上下文上限为 256K（262,144 tokens）；所选模型窗口或部署限制较小时，为协议和输出留出余量后取较小值。候选/原文结构视窗、历史外置和完整请求准入仍保留，增大配额不意味着自动填满上下文。接近完整请求窗口或明确的供应商 context overflow 先自动重建上下文并继续，见 CONTEXT；必要约束无法容纳时才如实报告，不能据此断言必须换更大模型。

知识状态除候选外包含 requirement、coverage facet、gap、evidence、counterevidence、judgment、feedback、question 和 pending operation。覆盖维度来自 query/工单/Wiki，并保留来源；Wiki 列表不是必须全部完成的无条件清单。无 Wiki 时由通用 Agent 从现有证据构造可修订的维度。

动作契约按实际工具能力组织，不把现有唯一 `ticket_decide` 数量永久固定。基线允许一次提交当前视窗内判断与后续动作批次：

- search：针对一个缺口提出关键词/向量表达、沿当前枚举继续，或新增独立分支。
- inspect：读取候选摘要视窗或指定来源字段/片段，说明待解决问题。
- delegate：请求具有明确目标的领域专家；不能自建无限子 Agent 树。
- clarify：持久化问题与依赖分支，允许自由回答。
- finish：提交覆盖与未决问题说明、确认结果版本和停止建议。

语义搜索的 `query` 可显式配 `mode=dense`，与独立搜索工具一致；关键词变更、语义改写与继续排名仍互斥。未指定数量的 adaptive 请求由模型依据用户范围、已有支持集合与下一次搜索的具体价值决定是否足够；不自动加上“评完所有候选”或“证明全库语义召回”的要求，也不设置固定数量替模型停止。

工具提交需要 operationId、上下文语义版本与引用；系统计数、权限、游标由服务端拥有。schema 与错误信息保持紧凑清楚，便于较小基底模型修正。一次错误返回具体字段/引用问题。主 Agent 另外提供 ticket_read（至多 8 个候选的概要/原文重读）与 ticket_search（明确查询或继续排名），二者仍走同一版本校验 Controller，不自动确认工单。每次版本化工具变更须等回执再继续，专家继续使用受限的 ticket_expert 搜索/读取/report。错误提示给出缺失 cN/eN 及重读方法；工具职责、参数互斥与错误修正参考 [Hermes tools runtime](https://hermes-agent.nousresearch.com/docs/developer-guide/tools-runtime)、[OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling) 和 [Anthropic 工具设计](https://www.anthropic.com/engineering/writing-tools-for-agents)。工具错误返回字段、引用与可恢复动作供模型纠偏，不按连续错误总次数停止。maxRepeatedToolErrors 默认 4，仅针对相同工具、规范化参数和相同错误、且期间没有有效动作或新候选/证据/判断的重复循环；参数变化、有效动作或输入修订会重新开始检测。state_id 的计量变化不算进展。主 Agent 和专家都移除固定动作/请求次数截止，专家旧 maxActions 仅保留为历史规划字段，不限制执行。专家先共享分配候选的已授权来源，仍按实际模型请求记录可见性；按独立范围并行，缺失事实才补读，完成后集中提交简短的逐条报告。累计 token 保留，时间和累计调用数不能代替语义停止。 不自动接受候选。

## 4. 持久调度与事务

当前 worker 在同机 Product Host 进程内运行。`ra_task` 保存原始要求、版本与当前 JSON 投影，`ra_task_command` 保存幂等命令和回执，`ra_task_event` 保存应用/领域事件，`ra_task_job` 保存执行权与重试，`ra_task_outbox` 同步 DSH 镜像，`ra_task_question` 保存问题及回答身份。以后可以拆 worker，但不改变语义契约。浏览器只提交命令/订阅，不拥有作业生命周期。

1. API 校验任务身份，将命令与 operationId 持久化并回执；重复命令返回同一结果。
2. worker 用租约与递增 fencing token 取得作业，事务外调用 DSH/Provider。
3. 调用返回后短事务核对租约及 fence、inputRevision 和 stateId；Provider 负责当前来源版本与权限。领域事件、投影与 outbox 原子提交；作业完成和后继作业在另一短事务原子登记，重启按已提交状态跳过已完成步骤。
4. 已提交后再向 UI 发布。网络“恰好一次”不作假设；工具可至少一次执行，状态效果通过幂等键去重。
5. 过期 worker 的迟到结果拒绝覆盖；可以记录审计，按新要求重新资格检查可复用的来源事实。

数据库 `DurableRetrievalAgentService` 每次操作从 SQL 装载状态，事务外执行 I/O，操作日志只在版本检查通过后提交。用户命令立即使旧作业 superseded 并增加 fence，不等待旧调用退出；即使底层忽略取消，旧输出也不能入库。相同 operationId/载荷返回原回执，换载荷则拒绝。Session 技术预览仍保留原 service 队列，但不参与数据库任务权威。

当前作业为 `search`、`agent`、`page`；默认同 Host 并发 4，租约 15 秒并每 1/3 租期续约，可重试错误最多执行 3 次。SQL `FOR UPDATE SKIP LOCKED` 取得租约，同一 Session 不同时启动两个执行者；进程内 Agent 创建/恢复另有 single-flight。输入变化或租约丢失取消当前 DSH/Provider 调用；强制退出后由租约到期回收。这些参数是可调整的资源边界，不是语义停止条件。

取消信号传至 Provider/模型入口；底层不能中断的数据库或模型计算仍可能运行，版本与租约隔离保证其结果不能迟到覆盖。重试区分可重试网络错误与条件不支持/权限失败，重试用尽保存明确 failure。现有排名 120 秒无响应仍需要队列、计算、取消到达与连接计时归因，不能只延长 deadline。

## 5. 全双工交互

用户补充首先进入权威状态，立即得到“已收到，正在复核”的可见回执。当前模型生成可在安全步骤边界接收更新；长调用不应挡住持久回执。问题包含 questionId、版本、影响范围和待答状态；过期回复不能回答另一个问题。

相关性标记被解释成反馈事件，再由 Agent 结合理由和来源判断：修订、保留原判并解释、补证或澄清。标记不直接写 confirmed/excluded。明确条件修改更新 queryRevision，受影响确认结果转为待复核，旧报告仍有版本但不再显示成最新。

只有依赖答案的分支等待。根任务可处于“部分分支待答，其他仍运行”；全部依赖阻塞时暂停计算，不默认给人类回复加过期倒计时。终态后的补充创建同一任务的新检索周期/结果修订，不悄悄改写旧冻结结果；明确“新任务”另建任务。

当前实现把待答主判断作业置为 waiting，已获 Provider 游标的独立 `page` 作业继续枚举且保留原 questionId。专家在 Finding 中提交问题后，主协调器可以立即继续并提出产品问题，其余独立专家继续运行；持久 worker 等这些分支结束后才释放当前租约。Host 替换时新 worker 从已持久化的 pending/running ExpertTask 重建子会话，保留分支身份、输入代次、额度和旧 manifest，跳过已完成分支；主 Agent 不重复推理或重新提问。纯上下文投影和计量发生提交冲突时，在同一输入版本下重算，最多重试 12 次，不重发 Provider I/O。条件修订或租约失效仍拒绝提交。分支粒度当前限于显式 ExpertTask，不是通用 DAG 调度引擎。

## 6. DSH 接线与恢复

当前 DSH 为 `0.1.5-rc.2`。读取日志使用 `snapshotEvents()`/`eventAt()`，按需查询序号而不持有可变事件数组。Persona 使用 prefix/suffix 配置，系统指令由 DSH V3 的 `system/message` 保存；上下文压缩分别替换连续的普通消息范围，保留系统头和历史系统增量。

JSONL 预览的已接受输入先以 `retrieval/input-accepted` 显示回执落盘，包含原消息 ID、原文和轮次，快查期间及无需模型的终态均可显示。只有 DSH loop 在开始步骤并写入系统消息后才准入对应 `user/message`；客户端看到同一消息 ID 后隐藏显示回执，避免重复。回执不进入模型表面或领域事件重放。数据库工作台继续从 SQL 命令和任务状态呈现用户输入。

安装版 DSH 的 followup、whenIdle、cancel、pre-step、ToolRuntime 与 Session 镜像已接通持久 worker。专家验收实际调用 rc.2 的 subagent spawn provider、skill register/get 和 userQuestions.ask；后者对被委派子 Agent 返回 DELEGATED_CALLER，因此专家通过 Finding 向主 Agent 转交问题。Cordis 插件作用域用 `ctx.get` 查询可选服务，不能假定根 Context 中可直接访问的服务在挂载 preset 后仍能直接访问。

优先使用公开子 Agent/provider 扩展创建领域上下文，不复制 DSH loop。专家子 Agent 的问题由主协调器转成产品 Question，避免假设所有子 Agent 都能直接调用根 UI 问题接口。Wiki provider 将目录/知识条目转换为可发现的专家和知识包，不假设文件监听就等于知识检索已接通。

任务库拥有产品状态，DSH Session 拥有模型会话；二者通过稳定身份、已提交事件引用及 outbox 协作，详见 [架构](../ARCHITECTURE.md)。启动恢复按 taskId/agentId single-flight，避免两个浏览器同时恢复出两个 Agent。

浏览器刷新：快照 + eventSeq + 增量订阅恢复结果和问题。Host 重启：重新取得作业租约，核对最后已提交步骤，恢复 DSH 会话；未确认完成的模型调用可重算，但不得重复提交结果。Database Provider 从 `ra_provider_snapshot` 恢复快照，并重新验证当前可信授权、来源/索引 generation；数据库快照不沿用 JSONL 演示的 15 分钟期限，旧数据库记录仅在这些身份检查通过后迁移该期限语义。来源已变化时明确失败并隐藏失效候选，已保存要求与补充继续可见，不悄悄绑定新来源。自动跨来源重绑是后续可验证的恢复策略，不能复用已失效结果冒充成功。

新一轮持久 Agent 作业开始时，将上一轮模型 surface 外置，再从当前 SQL 状态重新装配要求、用户反馈、证据与可用专家结论。原始事件日志仍完整保留；同一轮内保留最近工具错误供修复。这样避免条件修订后，上一轮最后的已失效专家 finding 继续作为紧邻模型消息被误采纳。

SQL outbox 推送完成不等于 DSH Session 已写盘。每次冷恢复都按 eventId 对照 SQL 全量已提交领域事件，缺失镜像可重建，同一 Session 的镜像同步 single-flight。提交后/推送前及推送确认后/Session 落盘前两种窗口都不会使 SQL 结果丢失；Session 内容没有反向覆盖 SQL 的权限。

模型无工具的纯文字结束不能成为最终交付。turn-stopping 经 DSH next-step inbox 自动提示模型提交当前证据判断，保留现有任务要求；连续两轮纠正后仍无结构化动作才记为具体的协议未完成。有效 decision 重置纠正计数，不用自动全选、解析模型自述或放宽业务范围制造成功。

## 7. 停止判断

每次 finish 需回答：当前用户要求是什么、哪些方向已查/被证据排除、仍未判候选影响什么、是否存在有价值的下一动作、为何此时停止。Controller 只验证可核验事实和合法性，不硬编码业务“足够”。

明确语义排除项在 QueryPlan 中保留完整原句及 `polarity=exclude`。模型 accept 前通过 `exclusion_checks` 对照每项原条件、或分支、已完成操作与剩余诉求，记录 applies、简短理由和已引用证据；主 Agent 与专家使用同一契约。Controller 只拒绝缺项、原条件被改写、无效证据，以及模型声称排除成立/不确定却 accept 的自相矛盾，不代替模型推断事实。核对产物随判断持久化，专家结果和当前上下文保留同一引用，重放不改变既有结论。旧计划没有此显式标识时继续按旧事件读取；新输入重新编译为当前计划。结构化自检不等于独立语义评测通过。

检查结束但范围内所有候选应排除时，使用 `no_result`，而不是要求至少一条确认的 `satisfied`。仍需当前页穷尽、候选全部判定及没有实质未决要求；Controller 不会为帮助结束而自动接受工单或放宽条件。错误回执明确完整原子判断未保存、正确结束方式及无需重读的有效证据；嵌套 action 被序列化成字符串时明确要求对象，避免错误地提示缺少 kind。

知识目录加载后（含空库）的 `finish.coverage` 明确 checked、remaining、nextAction、nextActionValue。存在影响答案的剩余要求或有价值下一动作时不能 satisfied/no_result；未完成则明确 partial。失败专家/带问题或未决 gap 的 Finding 需要主 Agent 在 expertReviews 中逐分支引用自己实际收到的证据并解释接手结果；不能略去失败分支，也不能用范围复核绕过在途专家或未解决逐条分歧。旧无目录事件保留原 finish 契约用于回放，新的公共 profile 使用扩展契约。

专家每轮从自己的持久 `ExpertTask.context` 重建工作窗，使用 ticket_expert 专用导航；工具错误后仍交付合法字段、候选与证据别名、续读位置和剩余额度。12 次动作包含最后一次 report；用完 11 次取证后只允许报告已有依据、未决项和下一动作，不强行改成确定结论。主 Agent 结束校验失败时列明未处理的 gap 与缺少 expertReviews 的 taskId，帮助模型修复具体问题。

冻结结果前在短事务中核对最新语义版本和已接受的命令：影响结果的反馈、条件修订或待答问题尚未处理时，不能用旧模型输出宣布满足。先完成有关复核，或如实停止为未完成；已经回执的用户输入不会因 finish 竞态丢失。纯索引维护/学习作业不阻塞本次结果交付。

同一关键词表达枚举完毕、多个搜索的新确认收益降低、主要业务分支有支持/反例、没有未解决的关键歧义，可共同支持停止；任何单一指标都不保证全局找全。要求全部时，枚举未完成或已知关键缺口不能标为满足；资源不足则停止为未完成并只交付已经确认的部分。

1～3 分钟不是自动 finish 规则。运行资源耗尽与语义满足分开，具体阈值经测试制定。没有进展的相同动作可去重并提示 Agent 重新决策；无效循环不以无限重试掩盖。

受控读取只需当前任务候选、明确字段和当前授权，不要求先读概览，也不把读取理由转成额外 depth gap。正式判断仍需要模型实际收到的引用。专家 inspect/search 不要求 report 专用判断数组。正式工作台的 finish.coverage 需求直接进入首次装配的模型 JSON Schema，避免目录尚未加载时缓存可选定义；当前必需的专家范围复核列在 actionState.finishRequirements.requiredExpertReviews 中，与结束校验共用判定规则。错误回执说明哪些判断未保存以及怎样修正。
