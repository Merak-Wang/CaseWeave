# Wiki 引用、专家配置与自动学习

Wiki 使用文件增量发布和 MySQL 持久学习作业。DSH 从复核结果提炼经验，经独立来源校验后自动发布，后续任务读取固定版本；报告与下载不等待学习完成。知识收益需通过独立任务对照评估。

## 1. 知识角色与目录

Wiki 是有来源的领域知识、检索策略和经验，不是工单事实数据库。专家通过知识包获得特定任务能力；没有 Wiki 时通用 Agent 正常工作。内容采用可编辑的 Markdown/结构化文件，索引和 embeddings 是可重建派生物。

已有 [工单检索 Wiki](../../wiki/README.md) 的导入基线包含 17 个领域、38 个条目，均标记为可否定的二手来源先验。[运行时读取](../../packages/agent-plugin/src/wiki-store.js) 与 [CLI](../../scripts/wiki-store.mjs) 共用固定版本校验，文件修改与学习则共用增量发布器；[接入说明](../../wiki/INTEGRATION.md) 记录 DSH 消费路径。[安全边界](../../wiki/SECURITY.md) 规定原始资料、私有盘点和发布目录分离，不导入企业操作脚本或权限配置。原库冲突、时效与未独立核验的权威性在条目中保留。

离线批次保留结构化 `expert.json`、`curation.json` 和领域 Markdown；当前所有运行消费者统一读取 `releases/<release>/entries/*.json` 中的 `bodyMarkdown`。自动经验同样进入发布条目，使用 `learned-…` 身份，不维护另一个只用于展示的 learned 目录。实际布局如下：

正文解释专有名词、业务关系、证据作用与具体反例。原始来源身份、路径、文件哈希和行段集中在库外私有 `provenance/`；运行时正文只保留知识身份和用途标记，通过 release、条目 ID、revision 及发布内容哈希关联私有追溯记录。构造场景明确标识为示例，不能当作工单事实引用。

```text
wiki/
  domains/<domain>/                 # 离线导入的可读说明与领域配置
  releases/<release>/manifest.json  # 领域、条目哈希、停用身份与操作摘要
  releases/<release>/entries/*.json  # 有 bodyMarkdown 的统一不可变条目
  current.json                     # 原子切换的当前指针
  previous.json                    # 上一完整发布的恢复指针
  .staging/                        # 未发布生成物，不进入读取端或 Git
  .publish.lock                    # 单机进程锁，不按超时抢占活跃发布者
```

人工编写和自动生成的条目共享检索与版本语义，不需要一个只供展示而不被 Agent 消费的旁路知识库。目录名和文件布局可优化，稳定的是条目身份、版本、引用和发布原子性。

| 对象 | 必须表达的内容 |
| --- | --- |
| ExpertSpec | id、domain、说明、触发提示、能力/工具范围、knowledgeRefs、prompt/skill 引用、schema 版本 |
| KnowledgeEntry | id、revision、类型、适用范围、正文、支持来源、反例/限制、状态、supersedes |
| Provenance | 来源任务/结果版本、反馈处置、工单/片段引用，或用户明确提供的领域定义 |
| Publication | baseRelease、新 release、增删改条目、校验结果、哈希、发布时刻和回退关系 |

专家配置不允许扩大 Provider 权限或覆盖系统安全规则；知识内容作为数据/任务参考加载。自动学习只产生允许的知识条目和策略补丁，不任意写代码、根 AGENTS 或工具权限。

## 2. 如何真正进入 Agent

快查询之后，Knowledge Service 先给主 Agent 轻量领域目录；路由后按明确引用和当前 gap 选择知识条目。专家收到特定 release 的内容和稳定引用，不一次加载整库。按目录/标签/关键词检索为基线，知识量增长后再评估向量召回，不能因知识向量索引不可用而阻断工单检索。

每次任务固定所消费的 Wiki release 和条目版本，模型 ContextManifest 记录实际收到的内容。文件修改或自动更新经校验后发布新 release，后续任务在快查后使用；进行中的任务不在同一轮悄悄混入新版本。紧急停用通过累计 revoked 清单使相关分支失效，在下一模型/工具边界要求重读或重新分派，不能改写旧引用含义；具体实现与时效边界见第 5 节。

Prompt 与知识引用分开：基础 prompt 维护判断/工具职责，领域条目提供边界和策略。修改 Wiki 就能改变后续专家的策略输入，验收需从实际模型请求和结果证明引用生效，不能以 UI 能保存文件代替。

## 3. 自动学习的证据入口

学习输入是已持久化轨迹的选择性摘要、逐条判断依据、用户反馈处置、搜索策略变化及结果版本。报告交付后排入持久学习作业，用户无需等待学习完成才下载。

| 信号 | 可以提炼 | 不能据此直接宣称 |
| --- | --- | --- |
| 用户“相关/不相关”反馈 | 需要复核的业务边界和例子 | 该标记本身是最终 Gold |
| Agent 复核后改判且有证据 | 适用范围、决定性字段、容易混淆之处 | 单例在所有产品/时期都成立 |
| 新 query 找到有据的相关工单 | 有效检索表达、适用条件、反例 | 多召回一定更准确或全局找全 |
| 超时、无效循环、冲突 | 检索失败经验与待改进策略 | 工具失败等于不存在工单 |
| 用户明确提供领域知识 | 带来源的领域定义/规则输入 | 它可以推翻已有工单原文事实 |
| Agent 自报成功、用户没继续说话 | 运行结局记录 | 搜索正确性已被独立验证 |

未能支持一般规律时，只生成受限的观察/待核查提示，或不形成新条目。自动学习也允许没有有价值的新知识，不用每个任务强写一条“成功经验”。

## 4. 增量提炼、校验和发布

采用“反思提炼 → 局部知识增量 → 自动校验 → 原子发布”的基线。参考 ACE 的条目化上下文、反思和增量整理以避免整篇重写；其论文也指出反馈质量和反思能力限制，不能把其基准收益直接当作本项目效果。[ACE 论文](https://arxiv.org/abs/2510.04618)、[方法与限制](https://arxiv.org/html/2510.04618v1)。

1. Reflect：读取指定轨迹/反馈的有效版本，区分错误解释、检索表达、决定性证据和未解决问题；只输出简短可核对的经验，不要求完整思维过程。
2. Propose：生成 add/update/deactivate 的条目级 delta，带适用范围、来源、反例、被替代条目和 baseRelease；不全库重写。
3. Validate：检查 schema、来源存在/权限投影、判断是否真正复核、引用是否支持表述、是否过度泛化、重复/冲突以及旧条目影响。确定性校验与模型证据复核结合；模型复核不等于绝对真值。
4. Publish：通过校验后自动写入版本文件/清单并切换 current 指针，记录任务及发布事件；**不等待人工批准**。并发写通过 release CAS/文件发布锁，旧 base 重新合并和校验，不能最后写入者覆盖其他增量。

文件读取和暂存写入按每批最多 4 项执行，保留清单顺序、路径/哈希/内容校验及每个文件的写盘同步；批内失败也等待已启动的操作全部结束再传播，避免释放发布锁后仍有后台写入。baseRelease 与已读取的当前版本相同时复用该校验结果，不重复读取同一批文件。Windows 发布目录 rename 的 EPERM/EACCES/EBUSY 可在持锁期间短暂退避，最多重试 4 次并响应取消；永久失败保留原始异常，不以随后读取不存在目标的 ENOENT 覆盖它。指针仍在完整验证之后才切换。
5. Consume：下一任务实际加载新 release，记录所用条目；没有匹配内容时零样本继续。

当前实现由 [wiki-learning.ts](../../packages/agent-plugin/src/wiki-learning.ts)、[wiki-publisher.js](../../packages/agent-plugin/src/wiki-publisher.js) 和 [task-store.ts](../../packages/agent-plugin/src/task-store.ts) 共同承担。只选择语义完成、当前访问有效的任务；候选必须有新输入后的 accept/exclude 判断，并明确引用同来源版本、实际交付给主模型的 `origin=source` 片段。生成/来源未知概览、未判定候选、纯反馈和资源中止不进入这个学习入口。最多选择 6 个已复核观察、每个 3 个片段；请求内截取片段保留实际起止与文本哈希。这是有意收窄的输入范围，尚未覆盖纯失败轨迹的策略学习。

提炼至多提出 3 条局部观察，每条再经独立 DSH 请求核对原始来源、适用范围和反例；允许输出空增量。条目使用 `retrieval-observation` / `evidence-reviewed-observation`，仍为非工单证据。确定性检查拒绝不存在的来源、字段越权、操作内容、循环替代和版本冲突。提炼/校验实际请求、输出、模型、token 和用时保存到 MySQL `ra_wiki_learning.details_json`；来源映射另随发布保存在 Wiki 根目录外的 `.cache/wiki-publications/<root-hash>/`，不送入专家正文。

`learn` 与 `unlearn` 复用持久作业的租约、fence 和重试，下载接口不等待它们；每个 Host 同时至多运行一个 learn，普通检索优先。辅助调用每次保留 3,000 输出 token 与协议余量，单次 120 秒资源边界只终止学习调用。文件全部写入暂存区并校验后才进入不可变发布目录；最后持有短 MySQL 来源事务完成指针替换。文件已提交而 SQL 回执丢失时，依据先前持久化的 delta 和发布操作摘要幂等恢复；新输入仍会撤下该旧来源的条目。

人工文件的不同条目修改按 baseRelease 合并，同条旧修改及被替代条目的并发修改拒绝。清单 `retired` 保留停用身份的最高版本与替代关系，后续发布和历史恢复继续检查关系图并递增版本；停用正文只存在于历史发布，不回到当前目录。只读端口的 `lineage()` 供发布器校验，不进入专家知识正文。自动增量在期间发生任何并发发布时重新提炼/语义校验，不把结构上可合并等同于语义无冲突。旧离线编译器只可初始化或重复校验自己的发布；同样经过发布锁，不能把新的学习结果指针改回旧批次。

校验失败的 delta 保留原因，自动修正或延后重试；不阻塞查询主流程。source/feedback/结果已经被新复核推翻时，旧学习作业不得继续发布过时经验。来源字段不能重放时，避免生成无从核对的普遍事实。

## 5. 冲突、反例与回退

当前工单证据优先于先验。发现矛盾先区分时间/产品/业务范围差异与知识错误：前者拆分适用范围，后者修订或停用旧条目，保留 supersedes 和反例引用。不能只增新条目而让旧错误一直被路由。

运行中记录条目使用、得到支持、遇到反例及与结果的关联，但使用次数/同意次数不是校准可信度。多条来源如果来自同一工单或同一自动总结，不算独立支持。循环引用不增加证据。

回退通过发布一个恢复旧条目集合的新 release，保留历史引用；不删除原始轨迹。当前读取器发现当前发布损坏时使用 `previous.json` 的完整版本并给出 warning；明确指定旧 release 的读取绝不换成另一个版本。有效反例的 `supersedes` 会让被替代条目退出新目录，新输入也会排入 unlearn 撤下旧来源经验。完整历史回退已有 CLI。基于留出效果退化自动选择整库回退仍需独立留出评测及决策入口，不能用发布完整性或模型自报成功代替质量评分。

Host 每 60 秒为已发布经验安排幂等 `source_check` 持久作业，普通检索优先。检查重新取得当前授权的快照，比较 Provider 与来源版本；有外部变化时自动停用旧经验，相同来源的新快照或仅时间流逝不构成事实被推翻。授权检查失败保留诊断和重试，不能据此虚构来源变化。检查不调用模型、不修改业务工单；实际执行时间受队列及 Provider 可用性约束。

发布清单额外维护累计 `revoked` 身份和最高版本，回退重新引入条目时必须递增版本，不能复活已停用的旧引用。主 Agent 决策前、专家上下文和工具提交前核对当前停用清单；受影响分支转为失败，撤销其候选旧判断及确认资格，拒绝旧 stateId 和迟到产物，并要求主 Agent 重读来源或重新分派。普通正文编辑继续遵守任务固定 release，历史发布仍可重放。该机制在持续运行的任务下一次模型/工具边界生效，不宣称能够抢占已经运行中的远端模型计算。

人工可直接维护领域文件，但它同样经过发布校验/版本记录；自动更新遇到同条并发人工修改时重新合并，不静默覆盖。

## 6. 验证学习是否有用

采用同模型、同数据、同任务的无 Wiki / 冻结 Wiki / 自动演进 Wiki 对照，按时间拆分学习轨迹和独立留出任务。留出答案、评分器和 Gold 不进入 Wiki 或运行上下文。人工审查评测样本用于建立质量依据，不是生产知识发布审批。

先证明“反馈 → Agent 复核 → 有来源的 delta → 自动发布 → 下次实际消费 → 新反例触发修订/回退”全链路。再比较确认精度、漏检、错误泛化、延迟与 token；与基线同样保留失败，不只报告新增知识条数。

这一能力改变推理时可引用的上下文，不等于模型权重训练。语言反馈记忆可以改善后续试验，但效果依赖反馈与任务分布，需要本项目验证。[Reflexion](https://arxiv.org/abs/2303.11366)。更换模型时需重新评估经验提炼和独立校验能力，必要时调整条目与策略。
