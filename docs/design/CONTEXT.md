# L0–L3 与上下文规划

完整候选与证据存储、模型工作视窗和界面窗口分别管理。L0–L3 分层、角色可见性与上下文清单共同约束模型可用证据；压缩不能改变结果资格或已读事实。

## 1. 分层含义

工单按四层组织，默认从标题和摘要开始判断。字段随来源映射，历史记录迁移按字段内容及来源身份处理，不仅依据旧层级名称。

| 层级 | 内容与用途 | 读取方式 |
| --- | --- | --- |
| L0 索引卡 | 稳定编号、标题、最少结构元数据/版本；历史定位和候选目录 | 默认轻量投影；标题是定位信息，不保证反映完整问题 |
| L1 概览 | 标题、摘要、必要已知字段、命中提示 | 首轮/当前工作视窗；缺失摘要如实标明 |
| L2 证据片段 | 与当前问题有关的来源字段/对话片段，附字段、位置、截断和哈希 | 按需检索/读取；摘要不足、冲突或原因排除时升级 |
| L3 完整详情 | 当前允许访问的完整正文/对话/处理记录及字段目录 | 可分段读取和浏览；不是不加过滤地输出整个 raw 载荷 |

L3 表示可用的完整受控详情，不表示一次模型调用必须接收全文。L2 是来源片段，不是再次生成的摘要；任何生成摘要单独标记为派生产物并保留来源引用。存储级原始载荷可以包含不可投影字段，不因名称带 raw 就整体放行或整体禁用。

普通查找以 L1 判断为默认，主/专家均可直接引用本条 cN 确认或排除。原文读取前先指出当前摘要未能解决的具体事实；只读涉及疑点的少量候选和必要字段，疑点解决就回到判断。不是所有原因/排除条件都自动要求深读；若概览已明确说明即可按概览判断。已有相互矛盾的证据不能忽略，仍需定向核实。关键词命中 1,195 条不意味着传入 1,195 条概要或读取 1,195 份原文；当前默认 8 条概要窗口，完整池在外部保存。

EvidenceRef 至少绑定 dataset/ticket/sourceVersion/field/span/contentHash。层级是展示策略，不是证据强弱分数。记录 Provider 获取、角色实际收到、用户查看三个独立事实；专家读过的片段不等于主 Agent 读过全文。

当前字段投影版本为 2，领域事件 schema 为 13。旧事件 5–12 按字段迁移：标题/摘要归 L1，已读正文字段归 L2；旧 L3 标签不证明全文已读。ESFT 标题声明为摘要派生；上游摘要的生成方式未声明，保留 unknown 与说明，不断言由模型生成。`summary` 即使通过深读端口取得仍是 L1；`source.raw_dialogue` 按说话人和原有顺序投影完整对话，L3 分段读取保持 part/start/end、字段总长与 spanHash，不输出完整 raw 对象。

## 2. 工作集与历史外置

CandidateStore 保留所有候选关系、当前资格、命中分支和最新判断。EvidenceStore 保存按需来源片段及引用；事件保存索引/变化，不逐轮复制整批内容。Prompt 不承担数据库职责。

数据库实现为 `ra_task_candidate/evidence/context` 三个不可变工件表，以 taskId + 内容 SHA-256 标识，保存来源身份索引。SQL 投影和领域事件中的正文替换为工件引用，事务边界水合并校验哈希，丢失/篡改拒绝恢复。逻辑 DTO 和 Session 镜像仍可水合完整集合；数据库工作台以服务端窗口读取候选，默认快照/页面最多 30 条，详情正文单独懒加载。完整工件外置与浏览器窗口分别控制，不把持久化等同于所有服务端消费者都已避免全量水合。

以每轮 100 个候选、20 个深读、持续 8 轮为例：后台可以保存全部历史身份及读取；第 8 轮只展开当前需要处理的 L1/L2/L3 片段。过去 7 轮保留覆盖变化、重要决定与可定位引用，必要少量 L0 标题；不用把旧 700 条的编号和标题全部塞回 prompt。

历史查阅通过“下一候选视窗、按 ID 重新读取、查看某覆盖方向证据”工具恢复。压缩后的语义总结只作导航，不能独立成为工单确认依据。重新需要某旧事实时取回原 EvidenceRef 对应片段，并核验来源版本。

## 3. token 预算

从实际模型 route 读取或配置上下文容量，按模型 tokenizer/可靠用量估算计算输入预算：

`B_input = C_context - B_output_reserved - B_protocol_margin`

输入再分为稳定规则/工具 schema、当前要求与更新、角色知识、覆盖与决定摘要、候选视窗、深读片段。输出额度、误差余量和分段比例都是配置假设；不直接采用模型宣传的最大上下文，也不假定所有供应商 token 计算相同。

规划步骤：

1. 固定当前用户硬要求、关键未决问题、角色目标和引用规则；这些不能为省 token 被静默删除。
2. 收集最新反馈和受影响判断、在途动作摘要、决定性的证据/反证。只固定有必要的少量引用，不固定所有历史正文。
3. 按角色任务和缺口选择当前候选，分配 L1 与按需深读额度。长片段先分段，不让一条工单挤占全轮预算。
4. 以新颖性、当前相关性、未处理时长和覆盖多样性排序，兼顾新候选与长期未处理候选；不永远只取分数最高的前几条。
5. 淘汰已完成工具载荷、过时 Wiki 片段和可重取的旧内容，再压缩历史行动摘要。重新计量后超限则缩小本轮工作集；连必要要求都放不下时明确容量问题，不能丢要求继续。
6. 持久化此次 ContextManifest：角色、状态版本、收到的候选/证据/Wiki 版本、片段范围与预算统计，供判断准入和复核使用。

基线先采用可解释的确定性选择和结构化摘要，再比较模型压缩的收益。即时检索、压缩、外部笔记和分离子 Agent 上下文可作为工程参考，但必须在本项目检查证据丢失与用量。[Anthropic context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。

当前工作集默认至多 8 个候选，以 12 个证据片段为基础窗口；配置了 token 预算时，允许窗口末尾同一工单、同一字段的后续片段一起进入，仍逐段检查预算。这样短对话不会仅因每句各有证据编号而被拆成多次模型往返；长字段保持续读和稳定别名，不把整池原文装入上下文。历史保留计数及最近 4 条判断/L0 导航。下一候选视窗按历史进入顺序取未见项；`inspect history` 按稳定 cN 重读，长字段按 `nextPosition` 续读。DSH Session surface 在有容量压力时压缩，保留最近四组完整模型/工具交换和校验错误，原日志不删。每次实际 `llm/stream` 从 messages.content 识别已发送片段，按渲染内容核验别名，生成 `measurement=dsh_request` manifest；规划用的 conservative_estimate 不能作为专家实际已读凭据。

模型主动深读时，当前候选焦点随请求切换到待读工单，最新原文优先进入工具回执与下一请求，不能被上一次摘要窗口过滤。用户在 UI 独立打开详情只记录用户可见性，不切换模型焦点。

专家拥有独立的候选/证据视窗与 nextPosition，保存在 ExpertTask.context，不能复用主 Agent 或另一专家的游标。每轮（含工具错误后的修复轮）重新交付当前角色的工作窗；紧凑 header 仍保留合法字段、续读位置和角色工具入口。读取结果不把内部 opaque candidateRef 作为模型应填写的 candidate_alias；导航统一使用稳定 cN。分支恢复保留旧 manifest，并从保存的取证位置继续。

工作集预算默认 `min(262144, capacity - min(6000, 0.4*capacity))`；实际请求计量使用本次 messages 的 DSH 估算与 system/tools 的保守估算，不把整个 Session 累计计量当作当前输入。预留输出及协议余量。Provider 返回的实际 input/output tokens 独立累计。估算不是模型 tokenizer 的精确值；连硬要求和待答问题都装不下时显式报容量不足，不改为无要求的摘要。

### 自动压缩与用量

容量错误必须与 token 吞吐限流、账期配额区分。`429`、`rate_limit_exceeded`、`insufficient_quota`、每分钟 token 限额和 billing 错误交回 DSH 原有错误/重试链，不因此压缩近期取证；“exceeded ... token ... limit”单独不足以证明输入窗口溢出。

上下文充足时保留近期已读来源；普通历史整理只计量 Session.deriveMessages() 中实际模型消息，不把 source.sections 与 content 中的同一正文重复计算；在 surface 估算超过模型/部署窗口的 65% 时触发，保留最近四组完整工具交换。1M 模型不再继承固定 256K 历史截止，避免尚有空间却重读未提交的阅读批次；这与单个工作视窗的 256K 上限是不同控制。主/专家完整请求达到模型或部署窗口的 85%（含输出预留）时，从权威任务状态重建较小工作集，保留要求、未决项与证据导航，通过 DSH request-error 的 retry 重新组装同一步。供应商明确返回 context overflow 时同样压缩后重试；普通网络/鉴权错误不误判为容量问题。最多四次递减重建，连必要要求都装不下时如实报未完成，不删除硬要求。正常检索不按累计 token 或经过时间取消生成。

这是确定性结构化压缩，参考 [Hermes 的载荷裁剪、完整工具组与尾部保留](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching/) 和 [OpenAI compaction](https://developers.openai.com/api/docs/guides/compaction)，没有让摘要模型重写证据事实。原始日志与 SQL 工件完整保留；补充条件后的过期专家产物只保留历史计数，不作为当前可采用 Finding。

budget.context 持久化最近一次完整请求的 estimatedInputTokens、可用的 provider measuredInputTokens、limit、reservedTokens 与 compactionCount；工作台圆环显示输入占窗口比例，点击可见明细。DSH TokenUsage 的 inputTokens 只指未缓存部分，实际输入必须加上 cacheReadTokens 和 cacheWriteTokens；缓存命中仍占上下文。主/专家使用同一求和规则。供应商尚无回执时标为估算，尚无请求时显示待测量。累计消耗另行计量，不能当作上下文占用。compression 分别记录 workingSetCount 与 capacityCount，新的压缩注记保留 working_set/window_pressure/provider_overflow 原因、触发前估算、阈值和窗口；旧 Session 注记按其实际类型分类。工作集整理不等于窗口已满。输出消耗按主 Agent 与所有专家（含旧轮次和失败调用）的供应商 outputTokens 回执累计，不加输入/cache tokens；报告/Wiki 不混入检索回路计数。

## 4. 多专家与判断准入

每个专家有独立 ContextManifest 和证据游标，按证据缺口决定何时报告，无固定 12/24 次截止。初始工作窗可读取主 Agent 对分配候选已取得的授权来源，实际请求仍记录本角色可见性。共享来源证据和并发 I/O，避免重复下载；不把其他专家完整对话复制进去。主 Agent 接收结构化 Finding、重要引用和争议，不接收全部子 Agent 工具历史。

逐条确认必须能追到至少一个实际执行判断的角色及其可见证据；批量提交允许，但每条具有明确引用和判断，不允许对没展示的排名区间一键确认。主 Agent 采纳专家判断时保存采纳关系，可在争议时取回原片段核对。

读取当前任务已授权候选的受控原文无需先读其 L1，也不把读取 reason 自动变成 model gap；实际读取与判断引用分别校验。actionState.finishRequirements.requiredExpertReviews 使用与结束校验相同的规则，列出全部当前失败或仍有问题/未决缺口的已结束分支，避免只显示最近六个 Finding 后漏掉较早的必需复核。

新反馈或条件变化使有关判断待复核，并提升涉及证据的读取优先级。旧轮次被压缩不影响反馈可定位性；同一证据别名不能因重新排序指向另一工单。

## 5. 压缩失败与降级

| 问题 | 行为 |
| --- | --- |
| 摘要漏掉否定、时序或反例 | 依据原片段纠正；保留失败样例，降低该压缩策略适用范围 |
| 正文超过单轮上下文 | 分段取证，显示已覆盖范围；不声称全文已读 |
| token 估计偏差、模型拒绝长度 | 减少可重取内容并重建 manifest；不删除用户要求 |
| 某工单长期没有进入视窗 | 通过未处理队列和覆盖优先级提升，记录候选饥饿指标 |
| 历史来源版本变化 | 重新取证/资格检查，旧判断不能无条件沿用 |

“几千条工单全部严谨复核且在 1～3 分钟完成”尚无性能证据。应通过批量判断、专家并发、按需深读和模型/工具优化逼近体验目标；若仍不足，报告未完成性质并继续改进，不能减少确认依据或暗中丢候选来凑时延。

## 6. 评测方式与可调整项

用多轮轨迹测试第 8 轮输入不随全部历史正文线性增长、早期决定性证据能重读、旧否定/反例不丢、反馈能定位、超长工具结果不溢出。对比不压缩、确定性压缩、模型摘要三种方式，记录任务结果、token、延迟、证据找回率和遗漏。

每种部署模型分别测量 schema 错误、压缩损失和证据找回率。层级投影、片段粒度、预算比例与压缩频率的修改应通过同任务对照验证，再同步源码契约与文档。
